# v3.53.0 — VPC Peering: the seventieth type closes the series

## New resource type: VPC Peering (`vpc-peer`, aliases `pcx`, `peering`)

- Browse peering connections — the 70th resource type, closing the
  four-type series (Managed Airflow, Transfer Family, Launch Templates,
  VPC Peering) driven by what real production accounts run.
- Status phrases per lifecycle state, with the two answers an operator
  actually needs: `pending acceptance: expires in 3d` — AWS silently
  expires unaccepted requests at 7 days, and the countdown IS the
  escalation — and the verbatim AWS cause for `rejected` / `failed`
  connections.
- An active-only CIDR-overlap warning names the clashing ranges before
  they silently blackhole traffic subsets. CIDR data only exists on
  active connections (an API quirk); every other state renders nil-safe.
- Two zero-API route checks annotate green rows from the already-loaded
  route tables: `no local route to peer` — an accepted tunnel nobody
  routes into — and `route to peer blackholed` — the other side tore
  down and your route now eats packets. No route-table list loaded, or a
  truncated one? No verdict — never a guess.
- The related panel answers "who actually routes to this peer" (the
  route tables referencing it; truncated lists show the honest `N+`
  lower bound), pivots to the LOCAL VPC through a symmetric membership
  gate — the cross-account remote side renders as plain OwnerId/VpcId
  facts, because a9s never pretends to see the other account — and jumps
  to the CloudTrail audit trail ("who accepted this").
- Demo mode ships 12 connections: a fully-routed showroom root, every
  lifecycle state including both transients, a CIDR-overlap pair, an
  unrouted active tunnel, and a blackholed route.
